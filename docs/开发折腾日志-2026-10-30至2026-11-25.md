### 一、国产手机浏览器的 Bilibili 播放器白屏：从浏览器差异追到 CSP 协议冲突

这件事前后跨了多轮排查，不能简单记成“修复了一个 iframe”。

**最初现象并不符合常见的浏览器兼容问题：**

- 电脑浏览器正常，手机 Chrome 正常，偏偏小米和华为自带浏览器在博客文章内嵌的 Bilibili 播放器白屏。
- 把同一个播放器地址直接复制到手机浏览器打开，却可以正常播放；说明播放器服务本身并没有整体不可用。
- 手机浏览器切换到“电脑版”模式后能够加载，但横屏仍然白屏。这个现象一度把排查方向带向移动版 UA、嵌入环境和第三方 iframe 的兼容性。
- 页面源码中确实有 iframe，宽高也正常；CSP 中看起来也已经允许 Bilibili 播放器域名。不能用“页面没生成 iframe”或“容器高度为零”解释。

**中间走过的弯路：**

- 先检查 iframe 是否存在、播放器 URL、容器尺寸和 CSP。
- 尝试过调整 iframe 的加载方式、`loading="eager"`、`referrerpolicy` 等属性，也测试过尽量精简的官方播放器 iframe。
- 这些尝试没有改变小米/华为浏览器的白屏结果。单元测试能通过，也不代表真实手机浏览器就能播放。
- 当时一度把怀疑重点放在移动 UA、sandbox 或主题强制懒加载上；这些属于排查假设，不能当作已证实根因。

**最后抓到的关键证据：**

浏览器控制台显示，页面实际请求的 iframe 地址是 `http://player.bilibili.com/`，而站点 CSP 只允许 `https://player.bilibili.com`。看起来域名相同，但协议不同，实际请求因此被 CSP 拦截。真正的问题不是小米、华为浏览器不支持 Bilibili，而是播放器地址协议与站点安全策略不一致。

这才把问题从“国产浏览器兼容性”缩小到可以明确验证的协议冲突。针对性方向是把 Bilibili 播放器地址规范为 HTTPS，而不是继续叠加 UA 判断、播放器参数或 CSS 补丁。

**后来又补出一个重要约束：**

11 月 7 日继续讨论 iframe 恢复逻辑时，用户明确要求 iframe 必须 100% 原样还原：src、全部参数、sandbox、loading、allow、referrerpolicy、尺寸等属性都要保留，不允许助手擅自增删或改写。排查还发现 `restoreIframeOnly` 仍会调用 `sanitizeHtml` 重新处理 iframe，这与“原样还原”的要求冲突。这里必须区分两件事：允许对播放器地址做明确授权的协议修正，不等于可以借恢复流程随意改写 iframe 的其他属性。

**复盘状态：** 根因已从真实控制台请求中定位；历史记录能确认曾提出 HTTPS 规范化方向，但不能证明最终修复已经在小米、华为真机上完成回归。因此本手记记录“根因找到”，不冒充“所有机型验证完成”。

### 二、首页置顶：反复比较后，把置顶数据与主题设置、全站缓存拆开

置顶不是简单地给文章加一个排序字段。真正棘手的是：管理员修改置顶后，首页要及时变化；同时不能让普通主题设置保存机制、共享 options 缓存或全站缓存把问题放大。

**一开始要先把问题边界厘清：**

- 这里讨论的是首页文章置顶，不是评论区管理员置顶；两套功能不能混为一谈。
- 置顶 CID 有自己的保存、读取、顺序和兼容需求，不应该为了更新首页而触发整套主题设置保存。
- 用户明确指出 `theme-pin.ts` 中的 `setOption()` 会带来 60 秒冷却，并要求去掉这条路径；同时明确不允许借机修改 `content.ts` 或缓存核心文件。

**方案逐渐收敛的过程：**

- 先讨论置顶 CID 是否继续存放在普通主题 options 中。问题在于它会跟主题设置读写和缓存机制耦合，写入后读回也可能受 options 缓存影响。
- 随后转向独立存储：把置顶 CID 放进专用 D1 记录（记录键为 `theme-pin:typecho-theme-oxn`），由置顶专用逻辑读写，而不是把它当成普通主题设置项。
- 写入后回读核验，确认数据真的落库；首页读取时优先使用独立置顶数据，同时考虑旧配置兼容和用户指定的置顶顺序。
- 缓存边界也单独讨论：置顶变化真正需要更新的是首页展示，不应该无差别清理文章页、独立页面或其他全站缓存。因此方案目标是让首页 HTML 缓存随置顶数据变化更新，尽量避免公共缓存失效范围扩大。

**前台置顶与后台主题设置：两条缓存刷新链路必须分清**

这部分是当时最容易被混为一谈、也最值得单独记录的地方。用户在 11 月 23 日明确指出：**前台执行置顶后首页没有及时刷新；普通主题设置与独立置顶 ID 是两条路，不能混在一起。** 这不是简单地“再清一次缓存”，而是要先确认每条路径实际写了什么数据、依赖哪一层缓存，以及应该通知哪些页面更新。

- **后台主题设置路径**：原有主题设置保存机制面向的是整组主题 options。它有自己的写入、共享 options 数据缓存和请求级缓存失效通知机制。历史排查中曾出现通过 `setOption()` 更新设置，再调用 `notifyEarlyRequestInvalidation()` 的做法；当时还讨论过 `domains` / `sharedDomains` 的失效范围。这个机制服务于普通主题设置，不能因为置顶数据需要刷新，就把独立置顶 ID 塞回去触发整套设置刷新。
- **前台置顶操作路径**：前台置顶/取消置顶应由 `src/pages/api/admin/theme-pin.ts` 独立处理，写入专用 D1 记录 `theme-pin:typecho-theme-oxn`；首页 `Index.astro` 读取同一份独立记录。成功写入后，刷新目标应聚焦首页 HTML 缓存，而不是无差别清理所有页面，也不应借用普通主题设置的保存入口。
- **为什么曾经“写入成功但首页不变”**：只把数据写进 D1，不代表已经通知首页缓存更新；只调用普通设置的失效通知，也不代表独立置顶数据的读取缓存同步更新。排查中曾发现前台置顶接口没有直接调用 `invalidatePublicCache()`，也曾尝试把内容缓存清理函数从 `content.ts` 引入置顶接口，但该方案后来按用户要求退回，没有作为最终实现保留。
- **缓存版本与作用域的反复调整**：中间方案先后出现过 `bumpCacheVersion()`、首页 `home` 域失效、共享 `options` 域失效，以及更早的 `sharedDomains: ['all']` 全量失效设想。它们不是同一套最终机制：全量失效会扩大影响范围；只刷新首页则必须确保首页读取的独立置顶数据不会继续命中旧缓存。最终讨论方向是置顶写入成功后递增缓存版本，并定向更新首页 HTML 缓存；普通 options 缓存不应成为前台置顶数据的权威来源。
- **后台设置刷新不能被误认为前台置顶刷新**：后台修改普通主题设置时，仍应保留主题原有的设置保存和缓存通知机制；前台置顶则应走独立 D1 写入与首页定向失效。两者可以共享底层缓存版本/失效基础设施，但数据源、触发时机和失效范围必须明确，不能让前台置顶绕回 `setOption()`，也不能为了置顶而破坏后台设置原有行为。

还必须记录一个当时没有完全消除的风险：即使前台写入绕开了 `setOption()`，若回读仍通过 `getOption()`，或者 `bumpCacheVersion()` 自身存在约 60 秒的版本 memo，其他实例仍可能读到旧状态；KV 数据缓存跨 PoP 也可能有约 30 秒传播延迟。因此，“D1 写入成功”“缓存版本递增”“当前实例首页刷新”“其他边缘节点也立即一致”是不同层次，不能用其中一项证明全部完成。用户实测仍有 60 秒冷却后，助手才承认早期方案虽然绕开了写入函数，却没有真正绕开 options 读取缓存/版本缓存链路。

**这段排查的真正结论**：后台设置保存机制要保持原样；前台置顶必须有自己的数据写入和读取路径，并且明确通知首页缓存更新。要同时验证后台改普通设置后原有刷新仍正常、前台置顶/取消置顶后首页及时变化、刷新后顺序正确，以及不同缓存实例是否仍有延迟。不能把“调用了缓存刷新函数”当成最终验收。

**为什么这套思路更合理：**

置顶数据的生命周期与主题外观设置不同；首页缓存也与全站其他页面缓存不同。把这几层拆开，才能避免一次置顶操作触发普通设置保存、共享缓存等待或全站缓存失效。它不是简单“换一种写法”，而是把数据职责、读取路径和缓存失效范围分清楚。

**真正踩过的坑：**

助手曾以为删除 `setOption()` 就等于绕过了 60 秒冷却，实际仍沿用了主题 options 的存储/读取路径，用户测试后发现冷却依旧存在。之后才承认必须沿着写入、读取、缓存版本和失效链路整体检查，不能只盯着某一个函数名。助手还曾错误汇报同步完成、问题解决，实际用户验证并不支持这个结论。

**复盘状态：** 独立存储、首页定向缓存失效是经过讨论后形成的架构方向；不同阶段的代码实现和线上表现必须分别看待。尤其 60 秒冷却问题，不能把早期错误实现或错误汇报包装成最终成功。

### 三、Markdown、Mermaid、MathJax 与 InstantClick：不是单次渲染，而是多个运行环境互相影响

这段时间大量精力花在同一份 Markdown 内容如何在不同环境中保持一致：

- 文章前台首次打开；
- InstantClick 局部页面切换后；
- Typecho 后台编辑器实时预览；
- 预览 iframe；
- 浅色与深色主题；
- Mermaid SVG、MathJax 数学公式以及普通代码块。

这些入口的 DOM、脚本生命周期和样式环境并不相同。一个入口修好了，不代表其他入口也正常。

**Mermaid 的问题不是只有“图表不显示”：**

- 前台与后台预览需要使用一致的公共配置，但又要根据明暗主题选择不同外观。
- SVG 的宽高、居中、背景透明、层级和布局测量会相互影响；容器尺寸还可能被页面过渡或尚未完成的布局计算干扰。
- InstantClick 页面切换后，脚本可能被重新执行；如果模块状态和脚本作用域处理不当，就会出现重复初始化、重试失控或变量重复声明。
- 因此排查不能只改 Mermaid 配置，还要看脚本何时执行、执行几次、执行时容器是否已经有尺寸。

**MathJax 的问题也不只是公式语法：**

- 处理过转义分隔符、显示公式垂直裁切、字体资源和预览 iframe 的存储隔离等问题。
- 公式在前台正常，不代表后台预览 iframe 的字体和资源环境也正常。
- 需要同时检查公式容器尺寸、字体加载时机和预览环境，而不是把所有异常归因于 MathJax 本身。

**InstantClick 放大了脚本生命周期问题：**

页面不是每次都完整刷新，原本依赖“页面加载时执行一次”的脚本，在局部切换场景下可能重复执行或状态残留。多轮修复中出现过重复声明、重复渲染和重试问题，期间也有恢复、撤销再重做的过程。

**复盘结论：** 这类工作真正的验收单位不是一个组件或一个测试文件，而是一张组合矩阵：前台首次加载、局部切换、后台预览、明暗主题、不同容器尺寸。早期助手有过只盯着单一入口修复、没有把整个矩阵跑完就继续叠加补丁的问题，造成了返工。

### 四、图片处理与灯箱：保留原主题行为，再修 OXN 自己的边界

图片相关问题牵涉文章、独立页面、首页笔记流和 InstantClick，不是给图片加一个点击事件就结束。

- 对照 Warm 原版时，重点是恢复原本的图片参数处理机制，而不是把 OXN 新增能力整体回退。
- 文章、独立页面和首页笔记流的图片处理入口并不完全相同；某处修好不代表其他内容流也会正确。
- 首页笔记图片灯箱还要考虑作用域，不能让一次点击影响页面其他图片。
- InstantClick 会改变页面切换和事件绑定时机，因此需要检查图片点击事件是否在切换后仍有效、是否重复绑定。
- 同一时期还处理了图片尺寸参数、灯箱点击和文章内容渲染之间的关系。

这里的关键经验是：先以 Warm 原版确认“原来应该怎样工作”，再只修 OXN 中被证实有问题的入口。不能为了让一个页面恢复，就把其他页面已经正常的 OXN 功能一起覆盖掉。

### 五、导航激活识别：从只看 URL，转向识别当前页面本身

导航激活状态的问题经历了多轮澄清。最初表现是某些独立页面只有特定别名加 `.html` 时才显示激活背景；换成 CID 或其他固定链接形式就不对。后来又提出自定义后缀也必须支持。

真正的要求不是不断扩充 URL 正则，而是：**识别当前正在显示的页面，再判断它对应哪个导航项目。**

排查中需要分清：

- 当前页面自身的 CID；
- 导航项目配置的 CID 或别名；
- 页面最终 URL；
- 自定义固定链接后缀；
- 目录式路径和子路径。

助手早期提出过在多个组件之间传递 CID、用正则匹配路径的方案，但用户质疑是否需要多改文件、是否会再次查库。进一步分析后也发现，简单 OR 匹配可能误判，甚至让多个导航项同时激活。用户还明确要求不能把 CID 额外渲染到导航栏，也不能破坏原有导航行为。

随后讨论方向才逐步明确：利用已有页面数据与导航项目建立对应关系，尽量在渲染层处理，覆盖 CID、别名和自定义后缀，而不是只认固定的 `.html`。

**复盘状态：** 需求边界和识别原则已经澄清，相关实现经历过调整；但历史记录中部分阶段没有完整构建和浏览器验证证据，不能宣称所有永久链接格式都已经无遗漏。

### 六、OXN 主题独立化：Warm 是参照，不是运行依赖

从 Warm 复制建立 OXN，不只是换主题名称。真正目标是让 OXN 可以独立维护，不会因为 Warm 或某个外部插件目录变化而失效。

- Warm 用来对照原有 DOM 结构、功能行为和样式细节。
- OXN 新增的导航、图标、设置、评论管理等功能应留在 OXN 自己的主题目录。
- 允许引用 OXN 主题自身目录中的文件；不能把外部主题或插件目录当成 OXN 的运行时依赖。
- 用户多次强调：修复某个问题时不要顺手重构其他机制，更不能把 OXN 已有功能整体回退到 Warm。
- 导航 DOM 的讨论尤其典型：用户指出 Warm 结构更简单，OXN 多套了几层；助手最初却把问题误解成 CSS 高度和图标对齐，直到用户再次强调“看 DOM 层级”才回到真正的问题。

这条主线贯穿后续设置、图标和导航工作：结构可以借鉴，功能边界必须独立。

### 七、Octicons 与自定义导航：既要统一外观，也不能破坏旧输入方式

图标工作不是简单替换 SVG。需要兼顾主题内置图标、用户自定义内容、旧标记语法、Octicons、新旧导航标题和页脚链接。

- 用户要求首页、文章、笔记等原有导航标题也能自定义，但不能改变主题设置原有保存机制。
- 图标和文字混排时，要保证 SVG 不被压缩，文字与图标的高度、基线和间距一致。
- 导航和页脚的输入字段职责不同：地址栏原功能不能变，文字栏原来的普通文字和旧图标语法必须保留，只能扩展新能力。
- 文章、独立页面、首页笔记流中的 Markdown GitHub Alert 也要使用统一图标渲染。
- 顶部明暗、搜索、登录快捷图标还要处理只显示一个图标时的定位，不能让单图标布局与多个功能图标布局偏离。
- 最终还核对过一个很具体的调用错误：GitHub 图标真实 ID 是 `mark-github`，不是 `github`；解析器支持 `title`，不需要为这个名称错误修改解析机制。

这部分最重要的教训是：扩展语法必须向后兼容，视觉统一也不能靠不断叠加 DOM 包装层。要同时看结构、尺寸、基线、窄屏和单图标状态。

### 八、评论区管理员置顶：前台按钮能点，不代表管理链路完整

评论区管理置顶与首页文章置顶是两套不同功能。前者涉及管理员身份、评论管理元数据、接口方法、CSRF 和前台交互。

当时的核心现象是本地有效、线上无效。排查不能只看按钮有没有显示，而要从前台事件一路追到接口：

1. 当前页面是否正确取得评论管理所需的元数据；
2. 当前用户是否被识别为有管理权限；
3. 前端是否发出预期请求；
4. 请求方法是否符合接口约束；
5. 后端是否完成权限与 CSRF 校验；
6. 最后是否真正写入评论置顶状态。

过程中讨论过独立管理元数据路由，但用户明确要求不要借机重构评论 API，也不能把 POST-only 的置顶接口擅自改成 GET。助手曾在实现方向上反复，用户要求后又恢复到此前认可的状态。

**复盘状态：** 这是一条必须端到端验证的管理链路。仅看到按键激活、接口文件存在或本地能用，都不能证明线上管理员置顶完整可用。

### 九、CoreDownload 解耦：从主题内置功能转为独立插件边界

CoreDownload 的工作重点是让前台下载能力逐渐脱离 OXN 文章模板，不再要求主题承担插件职责。

讨论和实现涉及：

- 独立运行时和公开数据接口；
- GET 请求约束；
- 文章可见性、密码保护和权限校验；
- 固定链接解析兼容；
- 独立页面挂载与旧主题组件清理；
- 插件样式作用域和 OXN 暗色模式适配。

这里反复强调一个边界：插件独立化不等于随意删除主题中仍在使用的东西；同步到主线也不等于把整个开发分支全部合并。必须按文件核对，明确哪些职责已经迁出、哪些旧组件可以安全移除。

### 十、主题设置导入导出与 WordPress WXR：保存行为必须由用户掌控

主题设置导入的关键决定是：导入 JSON 只回填当前后台表单，不直接发起写库请求、不自动刷新，也不另造一条保存路径。最后仍由用户点击原有保存按钮生效。这样才能保留主题原来的保存机制。

WordPress WXR 导入则是另一种规模更大的尝试，涉及文章、独立页面、草稿、分类、标签、评论、附件、时间、状态、增量导入、权限和事务。它的难点不只是解析 XML，还包括附件图片如何迁移到 R2，以及怎样在 Cloudflare/D1 环境下验证导入行为。因为图片迁移和完整运行验证没有证据证明完成，所以只能记录为功能尝试和待验证事项，不能包装成已经可用于正式迁站的工具。

### 2026-10-31（国产手机浏览器兼容性排查：Bilibili 播放器白屏）

- 这不是简单的“手机浏览器不支持 iframe”。当时反复对比了电脑端、手机 Chrome、小米浏览器和华为浏览器：电脑端及手机 Chrome 正常，问题集中出现在小米/华为浏览器的文章内播放器；手机浏览器切换“电脑版”后又能加载，横屏仍然白屏，而直接打开 Bilibili 播放器页面正常。
- 排查先核对了 CSP、页面中的 iframe 是否真实存在、播放器 URL 和 iframe 尺寸。线上页面中 iframe 和尺寸都存在，CSP 表面上也允许 `player.bilibili.com`，因此一开始很容易误判成浏览器兼容性或播放器参数问题。
- 曾尝试调整 iframe 的 `loading="eager"`、`referrerpolicy` 等属性（提交 `6d4d008`，涉及 `src/lib/markdown.ts` 和测试），但小米/华为浏览器仍白屏；仅保留 bvid 的精简 iframe 也无法解决。由此排除了附加参数、懒加载属性是主要原因。
- 后续控制台终于给出关键证据：实际 iframe 地址被输出为 `http://player.bilibili.com/`，而站点 CSP 只允许 `https://player.bilibili.com`。这意味着页面实际发起的 HTTP iframe 请求不符合 CSP，浏览器会拦截；真正的问题不是“小米/华为不支持播放器”，而是播放器协议与站点 CSP 允许列表不一致。
- 当时提出的针对性修复方向是在 `src/lib/markdown.ts` 的 iframe 转换逻辑中，把 Bilibili 播放器的 HTTP 或协议相对地址规范为 HTTPS。现有可检索记录能确认根因已经定位，但没有找到足够证据确认该 HTTPS 修复最终提交及小米/华为真机复测结果，因此不把它写成已完成验证。
- 这轮排查从“浏览器差异”一路追到实际 iframe 请求协议与 CSP 的冲突，花了多轮交叉测试。它的价值在于没有继续堆叠 UA 判断、播放器参数或 CSS 补丁，而是抓到了浏览器控制台中的真实拦截原因。

- 复盘结论：每次汇报测试结果，必须明确“测试的是哪个分支、哪个提交、哪个主题 ID”。分支名称相近、工作目录相似，都不能代替实际提交核对。

### 2026-11-22：多次误解用户指定的设置字段，扩展功能时必须保护原有输入语义

**错误一：把页脚链接设置误解成文章 Markdown 内容**

- 后来才确认真正需要处理的是 `linktxt/links`。

- 复盘结论：扩展旧字段时，必须先逐一确认字段职责、现有输入格式和兼容承诺；不能把“增加一种语法”做成“替换原有语法”。

**错误二：自定义图标的验证范围不够**

- 相关提交覆盖图标解析、导航、页脚和图标优先级，但当时没有浏览器测试记录。
- 复盘结论：解析单元测试通过不代表视觉位置正确。必须同时检查普通文字、旧图标语法、新 Octicons 语法、图标与文字混排、窄屏布局和页脚布局。

### 2026-11-23：置顶功能反复绕回主题设置存储，未真正解决 60 秒冷却

**错误一：没有抓住用户明确禁止的 `setOption()` 路径**

- 用户明确要求：`theme-pin.ts` 中必须删除 `setOption()`，因为它会带来 60 秒冷却；并明确要求不要修改 `content.ts` 和缓存核心文件。

### 2026-11-24：导航 CID 识别和 DOM 结构理解不到位，导致方案反复

**错误一：把导航激活识别简单理解为 URL 前缀匹配**

- 用户指出独立页面只有“别名 + html”时能显示激活状态，CID 和其他永久链接格式无法正确激活；并明确要求自定义后缀也应能工作。

- 用户真正强调的是识别页面内容与当前导航项之间的关系，而不是只比较地址字符串；同时不能额外显示一组 CID 数据，也不能破坏导航原功能。
- 复盘结论：不能先写一个看似可行的正则再要求用户试。应先梳理页面对象已有字段、导航数据来源、CID 与别名的对应关系，再确定最小修改点，并验证自定义后缀、目录式路径和子路径。

**错误二：没有理解用户拿 Warm 结构作对照的意思**

- 用户要求对照 Warm 主题的导航 DOM 结构，指出 OXN 多套了不必要的层级。
- 助手一开始把问题理解成 CSS/文字图标高度调整，只说保留现有 span，没有真正比较 DOM 结构。
- 用户再次指出 Warm 根本没有那么多层后，助手才承认没有理解结构对比，未继续改文件。
- 复盘结论：用户要求“对照结构”时，必须实际读取并比较两个主题的 DOM 层级，不应凭视觉印象先改 CSS。

### 2026-11-24 至 2026-11-25：主题显示、单图标定位和图标名称问题必须先定位再动手

- 用户反馈主题显示异常、顶部明暗/搜索/登录图标在只显示一个时位置不对，窄屏单图标位置与功能图标不一致。

- 用户要求先查清楚助手改了什么、为什么改变，再修复；不能一边猜原因一边扩大改动范围。
- 在 DOM 对比中，用户明确要求采用 Warm 更简洁的结构，而不是继续增加包装层。
- 另一个图标问题 `{{octicon:github|title=我在github}}`，最终核对发现图标库的真实 ID 是 `mark-github`，不是 `github`；解析器支持 `title`，因此这是调用名称问题，不应为此改解析机制。
- 复盘结论：主题显示、激活背景、单图标定位和图标命名是不同问题，不能混为一个 CSS 修复。每次只针对已定位原因修改，并分别验证宽屏、窄屏、单图标、多图标、当前页激活和明暗主题。

## 从这些失误中必须落实的开发纪律

1. **先复述边界，再操作**：本地文件还是 GitHub、哪个仓库、哪个分支、允许改哪些文件，开始前必须确认；用户说“只分析”就不执行写操作。
2. **先查实际代码，不按记忆猜**：每次改动前读取远端目标分支最新文件，并检查调用链、数据来源和现有机制。
3. **先确认问题，再给修改方案**：不能把猜测说成根因；有多个可能原因时先用证据排除。
4. **最小修改，不擅自重构**：用户限定只改渲染层、只改一个文件或不动核心机制时，严格遵守。
5. **保留原有功能**：新增图标语法、导航自定义、页面识别或设置导入时，旧输入格式、旧保存机制和原有权限规则必须继续有效。
6. **分支和测试结果必须绑定提交**：报告“已测试”时写明分支、提交和测试范围；没有执行就明确写“未运行”，不能用代码阅读代替测试。
7. **同步前逐文件核对**：不能把一个分支的局部文件同步说成整个分支合并；必须记录来源分支、目标分支、文件列表、提交和比较结果。
8. **错误由助手承担修复成本**：如果问题由助手的改动引入，应先定位并修复该改动，不让用户迁就错误结果，也不把返工说成用户需求反复变化。
9. **完成标准以用户实际验收为准**：代码提交、测试通过、浏览器显示正确、线上行为正确是不同层次，不能互相替代。
10. **日志要记录失败和返工**：失败方案、撤销、回滚、误操作和用户纠正都属于项目真实工作量，不能只留下漂亮的成功提交记录。
